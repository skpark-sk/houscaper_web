# Houscaper 제품 비전

> **한 문장 정의:** Houscaper는 누구나 형태를 놀이처럼 조각하면 BMC 규칙을 공유하는 건축 모듈이 즉시 조합되고, 전문가가 그 모듈 언어를 직접 만들고 검증할 수 있는 웹 기반 참여형 건축 게임이다.

## 1. 제품의 뿌리

Houscaper 논문의 질문은 “계산적 방법으로 유효한 모듈 건축 프레임과 외피를 만드는 참여형 설계 도구를 어떻게 구성할 것인가”였다. 연구가 제안한 답은 세 층으로 이어진다.

1. 일반 사용자는 복잡한 모델링 대신 간단한 공간 입력으로 형태를 만든다.
2. Boolean Marching Cubes(BMC)가 8개 코너 상태를 읽어 유효한 건축 타일을 배치한다.
3. 전문가가 타일셋·재료·단면을 정의하고 결과의 구조적 타당성을 확인한다.

웹 Houscaper는 이 연구를 “가벼운 SaaS로 공개한다”는 논문의 후속 과제를 플레이 가능한 제품으로 구체화한다. 논문에서 정한 기본 모듈 `900 × 900 × 540 mm`, 6단 적층의 `3240 mm` 층고, 표면 타일의 26개 대표 궤도, 건축 상태 `{0,1,2,3,4,5}`를 출발점으로 삼는다. 단, 사용자가 보는 것은 색 복셀이 아니라 완성된 프레임·바닥·창·개구부·기초 모듈이다.

## 2. 핵심 플레이어 판타지

**“손으로 몇 번 밀고 당겼을 뿐인데, 내가 선택한 건축 언어가 스스로 접히고 연결되어 작은 건물이 된다.”**

- **Townscaper와 다르다:** 즉흥 조형의 만족감은 계승하지만, 결과가 장식적 외피에 머물지 않는다. 동일한 BMC 위상 위에 실제 건축 모듈, 개구부, 바닥, 기초와 경량 구조 피드백이 결합된다.
- **Minecraft와 다르다:** 블록을 그대로 쌓거나 색칠하지 않는다. 입력 격자는 보이지 않는 조작 장치이고, 화면에는 연결 규칙을 통과한 일관된 BMC 모듈 메시가 나타난다.
- **CAD와 다르다:** 선을 정확히 그리고 명령을 외우는 대신 형태를 직접 만지고 즉시 결과를 본다. 정밀 저작은 Rhino/Grasshopper가 담당하고 웹은 놀이·조합·검증에 집중한다.

제품의 우선순위는 **건축 정확도보다 먼저 느껴지는 손맛**, 그리고 **손맛을 해치지 않는 범위의 건축적 신뢰성**이다.

## 3. 메인 경험 루프

`Play → Maker → Preview → Save/Share → Play`

1. **Play — 조각한다:** `index.html`에서 추가·삭제·밀기·당기기로 매스를 바꾼다. 변화한 국소 셀만 다시 해석되어 모듈이 살아 움직이듯 교체된다.
2. **Maker — 언어를 만든다:** Rhino/GH에서 만든 메시를 26개 BMC 슬롯/궤도에 배치하고 이웃 면 호환성을 확인한다.
3. **Preview — 관계를 본다:** 한 타일만 돌려보는 대신 회전·대칭 변형과 전후좌우상하 이웃, 작은 건물 샘플에서 끊김·충돌·빈틈을 확인한다.
4. **Save/Share — 보존하고 건넨다:** 초기에는 로컬에 1~2개 타일셋을 저장하고 JSON + 에셋 묶음으로 내보내거나 가져온다. 공개 시장 대신 파일/링크 공유만 제공한다.
5. **Play — 바꿔 입힌다:** 같은 매스를 유지한 채 호환되는 상대 타일셋으로 교체하여 “같은 규칙, 다른 건축”을 체험한다.

Maker는 Play와 분리된 연구 도구가 아니라, 플레이 중 선택한 문제 슬롯을 바로 고치고 돌아오는 짧은 왕복이어야 한다.

## 4. `index.html` 플레이 상호작용

`index.html`을 제품의 메인 플레이 페이지로 삼는다. 별도 데모 페이지로 핵심 기능을 흩뜨리지 않는다.

### 기본 조작

- **추가:** 빈 면 클릭/탭. 새 모듈이 바닥에서 살짝 솟고 주변 모듈이 짧게 재결합한다.
- **삭제:** 우클릭 또는 삭제 모드 탭. 대상이 안으로 수축한 뒤 사라지고 이웃이 새 위상으로 전환된다.
- **Push/Pull:** 면을 드래그해 한 모듈 단위로 확장·축소한다. 프리뷰 실루엣과 유효/무효 색을 드래그 중 표시한다.
- **창/개구부:** 벽 모듈을 선택하고 창 또는 개구부 도구를 적용한다. 연속 배치는 더 큰 사각 개구부로 묶되, 논문의 연결 규칙과 최소 연속 조건을 지킨다.
- **바닥/기초:** 높이와 지면 접촉에 따라 제안하되 자동 결정을 강제하지 않는다. 사용자가 후보를 순환할 수 있다.
- **실행 취소/다시 실행:** 모든 조작은 한 단계씩 되돌릴 수 있어야 한다. 무효 조작은 상태를 망가뜨리지 않고 이유를 한 문장으로 알려준다.

### 만족감을 만드는 피드백

- 변경된 모듈은 `scale + overshoot + settle`의 180~300ms 전환을 사용한다.
- 이웃 모듈은 30~60ms 간격으로 짧게 연쇄 반응한다. 전체 장면을 매번 재생하지 않는다.
- 교체 전후 메시를 짧게 크로스페이드하거나 접힘/펼침으로 연결해 팝핑을 숨긴다.
- 추가·삭제·창 삽입마다 재료감이 다른 짧은 사운드를 둔다. 모바일 햅틱은 선택 사항이며 끌 수 있다.
- 카메라, 선택 하이라이트, 그림자와 접촉 음영이 모듈의 실제 크기와 연결점을 읽게 해야 한다.
- 조작 중에는 복셀 박스를 기본 노출하지 않는다. 디버그 모드에서만 볼 수 있다.

## 5. 타일셋 Maker 모델

### 5.1 26개 슬롯과 궤도

표면 BMC의 256개 이진 구성 중 점-점/모서리-모서리만 닿는 구성을 제외하고, 수평 회전과 대칭으로 같은 형상을 묶으면 26개 대표 슬롯이 남는다. Maker는 이 26개를 타일셋의 공통 문법으로 사용한다.

각 슬롯은 다음을 가진다.

- 대표 `configId`와 8코너 비트열
- 해당 슬롯이 담당하는 회전/대칭 `orbit`
- 역할(`roof`, `wall`, `floor`, `extra`)
- 메시 변형, 재료, 피벗
- 여섯 면의 공유면 서명
- 선택적으로 프레임 선과 개구부 앵커

건축 타일셋은 이 표면 문법 위에 `base=1`, `floor=2`, `foundation=3`, `opening=4`, `window=5` 기능 변형을 얹는다. 처음부터 `6^8` 전체 조합을 구현하지 않고, 실제 플레이에 필요한 검증된 변형만 슬롯의 `variants`로 추가한다.

### 5.2 공유면 서명과 “상대/호환 타일셋”

두 타일은 맞닿는 면의 네 코너 상태, 경계 윤곽, 연결 앵커가 같을 때 호환된다. 이를 정규화한 값을 `faceSignature`로 저장한다.

“상대 타일셋(relative/compatible tileset)”은 메시 모양과 재료는 다르지만 다음을 공유하는 세트다.

- 동일한 26개 대표 슬롯과 orbit 해석
- 동일한 코너 순서 및 축 규약
- 맞닿는 면의 호환 서명 체계
- 동일한 모듈 치수 또는 명시적으로 허용된 비례

따라서 플레이어는 매스를 유지한 채 타일셋을 바꿀 수 있고, Maker에서는 현재 타일 주위에 다른 세트의 상대 타일을 배치해 경계가 이어지는지 바로 확인할 수 있다.

### 5.3 Maker 화면의 최소 기능

- 26슬롯 완성도 그리드: 완료/누락/오류
- 선택 슬롯의 원본, 4방향 회전, 대칭 orbit 미리보기
- 상·하·좌·우·앞·뒤 이웃 후보 자동 배치
- 같은 세트와 상대 세트를 나란히 또는 혼합 배치
- 면 경계 오버레이, bbox, 피벗, 법선, 구조 앵커 표시
- 작은 접촉 시트(contact sheet) 자동 생성

호환 점수는 단순하고 설명 가능해야 한다.

- **100점 시작**
- 필수 슬롯 누락: 즉시 실패
- 공유면 코너/윤곽 불일치: 해당 연결 실패
- 앵커 거리·방향 오차: 감점
- bbox/피벗/축/단위 오류: 가져오기 실패
- 경미한 시각적 틈이나 재료 차이: 경고만

점수보다 중요한 출력은 “`slot 12의 +X 면 윤곽이 neighbor slot 7의 -X 면과 다름`”처럼 고칠 수 있는 오류다.

## 6. Rhino/GH → Web 에셋 계약

Rhino/Grasshopper는 권위 있는 형상 저작 환경이다. 웹 가져오기는 임의 OBJ 파일을 믿지 않고 아래 계약을 통과한 **완전한 모듈 단위**만 받는다.

### 6.1 내보내기 단위

- 파일 하나 또는 명시된 scene node 하나가 슬롯 하나의 완전한 모듈이어야 한다.
- 프레임, 바닥, 창틀 등 여러 부품은 모듈 안의 named child/material group으로 유지한다.
- `slotId`, 기능 variant, 재료 역할과 구조 앵커를 manifest에 기록한다.
- 가능하면 glTF/GLB를 기본 교환 형식으로 사용하고 OBJ는 검증 가능한 보조 입력으로만 둔다.

### 6.2 필수 검증 체크리스트

- [ ] **완전한 모듈:** 파편·단일 면·임의 오브젝트 조각이 아니라 의도한 슬롯 전체가 포함됨
- [ ] **기대 bbox:** 기본 모듈 `900 × 900 × 540 mm` 또는 정규화된 `0.9 × 0.9 × 0.54 m` 범위와 허용 오차 일치
- [ ] **단위:** source unit이 `mm` 또는 `m`로 명시되고 웹에서는 한 기준 단위로 변환됨
- [ ] **원점/피벗:** 모듈 기준 코너 또는 합의된 중심에 정확히 위치
- [ ] **축:** Rhino의 Z-up에서 웹 좌표계로 변환 규칙이 명시되고 좌우 반전이 없음
- [ ] **형상 품질:** NaN, 퇴화 삼각형, 중복 정점 폭증, 뒤집힌 법선, 예상 밖 비-manifold 경계 검사
- [ ] **슬롯 ID:** 26개 대표 슬롯 및 variant와 manifest가 일치
- [ ] **공유면:** 각 면의 코너/윤곽/앵커 서명을 추출할 수 있음
- [ ] **썸네일:** 고정 카메라·조명으로 슬롯 썸네일 생성
- [ ] **접촉 시트:** 전체 슬롯과 대표 이웃 조합을 한 장에서 육안 검수
- [ ] **완성도:** 필수 슬롯 누락, 빈 메시, 극단적 triangle count가 없음

`22.3dm`에서 오브젝트 조각 단위로 OBJ를 내보냈을 때 건축 모듈 대신 debris가 생성된 경험은 이 계약의 핵심 검증 사례다. 가져오기 단계는 **“크기가 맞는 완전한 슬롯 모듈인가?”**를 통과하지 못한 파편 묶음을 플레이 에셋으로 등록하지 않아야 한다.

## 7. 경량 구조 분석

목표는 Karamba를 브라우저에서 재현하는 것이 아니라, 플레이어가 명백한 구조 위험을 발견하고 다음 행동을 선택하게 하는 것이다.

### 7.1 모델

1. 타일의 구조 앵커와 선형 부재를 합쳐 전역 **frame graph**를 만든다.
2. 지면/기초 접촉 노드에 pin 또는 fixed support를 지정한다.
3. 자중, 바닥 면하중의 등가 절점하중, 한 방향 풍하중을 적용한다.
4. 재료(초기 steel/timber)와 단면의 `E`, 면적 `A`, 선택적으로 `I`, 허용응력을 사용한다.
5. 작은 모델은 2D/3D truss 또는 단순 beam-frame solver로 축력, 변위, 이용률을 계산한다.

### 7.2 피드백

- 부재 색: 낮은 이용률 → 높은 이용률 → 초과
- 변형 형상은 과장 배율로 별도 토글
- 불안정/고립 노드, 지지점까지 하중 경로가 없는 영역 표시
- “기둥 추가”, “기초 연결”, “단면 확대”처럼 한 단계 제안

### 7.3 명확한 한계

- 개념 설계용 상대 비교이며 인허가·시공 판단용이 아니다.
- 접합부 강성, 좌굴, 진동, 화재, 비선형, 판/쉘 거동, 상세 풍·지진, 지반과 현장 조건은 초기 범위 밖이다.
- 결과에는 solver 가정, 단위, 경계조건과 “전문 구조 검토 필요”를 항상 표시한다.
- 해석 실패를 억지 숫자로 보여주지 말고 singular/불안정 상태로 설명한다.

```json
{
  "schema": "houscaper.tileset/0.1",
  "id": "solkyu.ffmm-light",
  "name": "FFMM Light",
  "version": "0.1.0",
  "author": "Solkyu Park",
  "topology": {
    "family": "bmc-26",
    "cornerOrder": "houscaper-v1",
    "upAxis": "Z",

    "unit": "mm"
  },
  "slots": [
    {
      "slotId": 0,
      "configId": 1,
      "orbit": [1, 2, 4, 8],
      "role": "floor",
      "mesh": "meshes/slot-00.glb",
      "pivot": [0, 0, 0],
      "faces": {
        "+X": "bmc4:0011",
        "-X": "bmc4:0000"

      "variants": {
        "base": "meshes/slot-00-base.glb",
        "foundation": "meshes/slot-00-foundation.glb"
      },
      "structure": {
        "nodes": [[0, 0, 0], [900, 0, 0]],
        "members": [[0, 1, "steel-rhs-150x50"]]
      },
      "thumbnail": "thumbs/slot-00.webp"
```

실제 공유 묶음은 manifest JSON, GLB, 썸네일만 포함한다. 초기 버전에는 계정, 결제, 거래 메타데이터를 넣지 않는다.

## 9. 아주 작은 단계별 MVP

### Stage 1 — Playable feel first

- `index.html`에서 국소 BMC 갱신과 일관된 건축 모듈 메시 1세트
- 추가/삭제, push/pull, undo/redo
- 만족스러운 전환·선택·카메라 피드백
- 창/개구부 한 종류
- 데모 목표: 3분 안에 작은 건물을 만들고 계속 만지고 싶다

### Stage 2 — Maker

- 26슬롯 import/배치/회전/대칭
- 에셋 계약 자동 검증과 접촉 시트
- 이웃 및 상대 타일셋 호환 프리뷰
- Play에 즉시 적용

### Stage 3 — Save/Share

- 브라우저 로컬에 1~2개 타일셋 저장
- JSON + 에셋 bundle export/import
- 읽기 전용 공유 링크 또는 파일 전달

### Stage 4 — Structures

- 구조 선/앵커가 포함된 한 세트
- 지지점·자중·단순 하중과 소형 truss/beam 해석
- 이용률/불안정 시각화와 한계 고지

각 단계는 앞 단계의 플레이 감각을 훼손하지 않을 때만 다음으로 넘어간다.

## 10. 아직 만들지 않을 것

- 전체 `6^8` 건축 조합 또는 무거운 WFC 생성기
- 무한 월드, 대규모 도시 시뮬레이션
- 판매자 계정, 결제, 경매, 평판을 갖춘 마켓플레이스
- 동시 편집, 소셜 피드, 채팅
- 브라우저 안의 완전한 Rhino/GH 대체 모델러
- 상세 BIM, 견적/CPQ, 시공 도면 자동화
- 쉘/솔리드·비선형·좌굴까지 다루는 full FEA
- 모바일 햅틱과 사운드의 과도한 커스터마이징
- AI 자동 건물 생성이나 최적화

## 11. 성공 기준과 관찰 가능한 데모

첫 공개 데모는 다음 장면을 끊김 없이 보여줘야 한다.

1. 사용자가 `index.html`을 열고 기존 작은 건물을 즉시 이해한다.
2. 클릭과 드래그로 10회 이내에 형태를 확장·깎고 창과 개구부를 만든다.
3. 모든 변화가 짧은 연쇄 애니메이션으로 반응하며, 색 복셀이나 파편 메시가 최종 표면에 보이지 않는다.
4. 같은 매스에 두 번째 상대 타일셋을 적용해 외관은 달라져도 연결은 유지됨을 확인한다.
5. Maker에서 한 슬롯을 선택해 이웃/회전/대칭과 호환 오류를 확인한다.
6. 타일셋을 저장·내보낸 뒤 다시 가져와 같은 결과를 재현한다.
7. 구조 보기에서 지지되지 않은 부분을 찾고 기초/프레임을 추가하자 경고가 개선된다.

측정 가능한 최소 기준:

- 첫 유효 조작까지 10초 이내
- 일반 조작의 화면 반응이 즉각적으로 느껴짐(목표 100ms 이내 프리뷰, 전환은 별도)
- 필수 26슬롯 누락 및 파편 에셋을 import 단계에서 100% 차단
- 기준 접촉 시트에서 공유면 관통/틈 오류 0건
- export → import 후 topology hash와 배치 결과 동일
- 구조 해석이 지원 범위 밖일 때 잘못된 “안전” 판정을 표시하지 않음

## 12. 현재 구현과의 차이, 교정 방향

| 현재 상태 | 제품 비전과의 불일치 | 교정 방향 |
|---|---|---|
| `index.html`은 이진 voxel set에서 색이 섞인 단일 surface mesh를 재생성 | 메인 화면에 건축 BMC 모듈이 없고 colored-voxel painter처럼 읽힘 | `index.html`을 메인 shell로 유지하고, lookup 결과에 검증된 모듈 GLB 인스턴스를 배치 |
| multi-tileset 경험이 `townscaper.html` 링크에 분리 | 핵심 Play ↔ Maker 흐름이 메인 페이지에서 끊김 | 검증된 기능만 `index.html`로 통합하고 보조 페이지는 reference/debug로 축소 |
| `bmc-data.js`는 26타일/256 lookup을 잘 보유 | topology는 있으나 실제 모듈 에셋·공유면 계약이 없음 | 기존 lookup을 공통 문법으로 재사용하고 slot manifest와 face signature를 연결 |
| `tilesets.js`의 `ffmm`은 기능별 대표 OBJ 하나를 가리킴 | 26 슬롯/orbit 전체 및 이웃 호환성을 표현하지 못함 | manifest 기반 슬롯 배열과 variant 구조로 전환 |
| `22.3dm`은 mm, `ffmm.3dm`은 m이며 layer taxonomy도 다름 | 단위·레이어 이름에 의존한 import는 교환이 불안정 | source unit/axis/pivot/slotId를 manifest에 강제하고 정규화 |
| `22.3dm` 파편 OBJ가 debris로 보임 | 파일 존재를 모듈 완성으로 오인 | bbox·완전 모듈·slot ID·접촉 시트 검증을 등록 전 gate로 적용 |
| `structural-view.html`은 BMC edge를 프레임처럼 시각화 | 실제 지지·하중·강성·solver가 없어 “analysis”라 부를 수 없음 | 우선 frame graph 메타데이터를 정의하고, 작은 검증 모델부터 solver 추가 |
| Maker, 저장, 공유 데이터 계약이 없음 | 타일셋을 만들고 교환하는 핵심 루프가 닫히지 않음 | 서버 없이 로컬 저장 + bundle import/export부터 구현 |

기존 코드의 가장 재사용 가치가 높은 자산은 `bmc-data.js`의 26개 대표 타일과 256 lookup, 그리고 유효하지 않은 점/모서리 연결을 차단하는 규칙이다. 교정은 이를 버리는 재작성보다 **실제 모듈 에셋 계약을 그 위에 연결하는 방향**이어야 한다.

## 13. 열어 둘 결정

1. **웹 기준 좌표/단위:** 내부 단위를 meter로 통일할지 millimeter로 유지할지 결정한다. 어느 쪽이든 import manifest에는 원 단위를 보존한다.
2. **기본 교환 형식:** GLB를 필수로 하고 OBJ를 변환 입력으로만 둘지 결정한다.
3. **건축 variant의 첫 범위:** 26개 base 슬롯 전체 뒤에 window/opening/floor/foundation 중 어떤 두 기능을 먼저 완성할지 정한다.
4. **큰 개구부 규칙:** 연속 window/opening을 여러 모듈의 시각적 묶음으로 처리할지, 별도 span module로 내보낼지 정한다.
5. **첫 구조 solver:** axial-only 3D truss로 시작할지, 회전 자유도를 포함한 단순 frame으로 시작할지 정한다. 데모 신뢰성을 위해 구현 전에 기준 해답이 있는 작은 모델을 먼저 고른다.

### 제품 원칙 요약

- 보이지 않는 입력은 단순하게, 보이는 결과는 건축적으로.
- 형태 변화는 즉시, 모듈 교체는 만족스럽게.
- Rhino/GH는 저작의 기준, 웹은 놀이와 검증의 접점.
- 호환성은 “비슷해 보임”이 아니라 공유 topology와 면 서명으로 설명.
- 구조 결과는 가볍되 정직하게.
- 기능 수보다 하나의 완결된 `Play ↔ Maker ↔ Preview ↔ Save/Share` 루프를 먼저 만든다.
